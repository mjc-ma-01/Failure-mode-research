# Roadmap

整理于 2026-10-13。本文件是当前的总计划；各模块细节见对应目录的 README。

## 研究问题

在正常任务（无恶意用户、无攻击输入）中，agent 会出现哪些失败模式；对每一类，
**放在 harness 侧防御**和**让模型自己学会**，哪一种更有效、代价更低？

## 第一部分：evolve harness（改协议，不动权重）

状态：目录与论文代码已就位，评测链路待实现。

1. **基线**：`load_ckpt` 加载 Qwen3-8B，固定权重，在 `data/` 选定 bench 上跑一批任务，
   记录失败模式、harness 拦截情况、独立判定的危害。
2. **出证据**：把 episode 统一成同一种记录（动作 / 观测 / 拦截 / 状态变化 / 危害判定）。
3. **进化**：harness 编辑器基于证据生成候选协议；候选在 search 集上跑，过安全与效用门后
   才进 dev 面板；拒绝则回滚保留 parent。
4. **复测**：在封存的测试集上比较进化前后的效用、危害、拦截率与执行成本。
5. **结论**：给出"哪些失败模式被 harness 消掉"的清单，剩下的交给第二部分。

起点是 `evolve/harness/upstream/EvoSafeHarness`（冻结模型、只搜 harness；论文与仓库说明见模块 README）。

## 第二部分：model 侧（待整理）

状态：按计划先留空，接口与问题清单见 `evolve/policy/README.md`。

方向是把第一部分筛出来的失败模式转成模型侧能力：

- harness-use SFT，再用 harness-augmented GRPO 内化；
- 关键对照：撤掉 harness 后模型是否还守得住（避免把 harness 的功劳记到权重上）。

## 工程约定

- `data/` 只读；需要改数据就写适配器或数据集副本，并记录来源与哈希。
- 测试集封存，只允许最终一次测量；dev 面板只能做诊断。
- 失败标签规则**先预注册再跑搜索**（`FAILURE_LABELING.md`），标签不可事后修改。
- 每次候选、每次训练都要留回执：版本、分数、拒绝原因、预算消耗。
- 预算要记账：GPU 小时、API token、episode 数三项分开记。

## 已知约束

- 共享卷剩余空间约 171 GiB，大轨迹文件要控制体量或另找落盘位置。
- 集群为单卡 H200；旧工程记录过"设备被他人进程占用"的问题，提交前先做占用检查。
- 本项目当前**没有版本控制**。建议在动手写实现前 `git init` 并做一次初始提交。
- 上一轮实验（已移出本项目）留下了可复用的工程约束：候选要按实测效用与危害决定去留、
  dev 只作诊断、测试集封存。但它的结论属于旧任务集，不要直接引用为本项目的结论。

## 下一步（按顺序）

1. 定稿失败标签规范（`FAILURE_LABELING.md`）并实现确定性 checker——这是 ground truth，
   先有它再谈其他。
2. 确认第一批 bench 与任务格式（先小：每 bench 几十条）。
3. 写 `load_ckpt` + episode 运行器，只跑基线，出标签构成诊断报告。
4. 定义 `Harness` 与候选编辑器的边界，按 EvoSafeHarness 的搜索循环实现最小闭环。
5. 跑通"候选 -> 搜索 -> 接受/拒绝 -> 复测"，再谈规模化。
