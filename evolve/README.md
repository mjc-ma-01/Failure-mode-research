# evolve

本项目的主实验模块，分两部分。两者都从**同一份失败证据**出发，改动的东西不同：

```text
                 +-----------------------------+
   失败证据 ----> | A. harness 进化（改协议）    | --> 新的 harness，权重不变
   （episode）   +-----------------------------+
                 +-----------------------------+
             ---> | B. policy 更新（改权重）     | --> 新的模型，harness 不变
                 +-----------------------------+
```

| 子目录 | 改什么 | 回答什么问题 | 现状 |
|---|---|---|---|
| `harness/` | 执行侧的检查与协议（有序、可执行的程序） | 哪些失败模式能被 harness 挡住？ | 论文代码（EvoSafeHarness）已就位，链路待实现 |
| `policy/` | 模型权重（SFT / RL） | 哪些必须让模型自己学会？ | 占位，第二部分再整理 |

## 为什么这样分

同一个失败模式（例如"证据不足仍宣称任务完成"）在两种做法下的结论完全不同：

- 如果加一条可执行检查就能稳定挡住，且不损失正常任务的效用，它属于 harness 侧；
- 如果挡不住，或者挡住了但模型仍然学不会正确做法（一撤就犯），它必须回到模型侧。

因此每个候选项都要用同一套指标报告：任务效用、实际危害、拦截率、执行成本。
只看"事故率下降"会把 harness 的功劳误记到模型头上。

## 数据流

```text
data/<bench>  -->  统一任务格式  -->  基线 episode（固定 ckpt）
                                          |
                          +---------------+---------------+
                          v                               v
                  harness 编辑器                    训练数据构造
                  （候选协议 -> 搜索验证 -> 接受）    （SFT / RL，待整理）
                          |                               |
                          v                               v
                   进化后 harness                   更新后权重
                          +---------------+---------------+
                                          v
                                在测试集上复测
```
